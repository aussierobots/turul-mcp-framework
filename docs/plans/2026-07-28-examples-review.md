## New examples the 2026-07-28 spec warrants

Each proposal names **why it should exist**, the **learning value** for a human
reader, the **spec match** (the driver-doc table it demonstrates), and its
**practical usefulness**. None exist today in any form.

### 1. `subscriptions-listen-server` + `subscriptions-listen-client` (pair)

- **Why**: `subscriptions/listen` is THE replacement for the entire 2025
  GET-SSE/resumability model — the single biggest conceptual shift for anyone
  migrating — and no example demonstrates either side of it.
- **Learning value**: ack-first protocol (`notifications/subscriptions/acknowledged`),
  filter shape (`toolsListChanged`/`resourcesListChanged`/`resourceSubscriptions` URIs),
  `io.modelcontextprotocol/subscriptionId` stamping, and the reconnect-on-drop
  idiom (stream state is request-scoped — clients re-issue, they don't resume).
- **Spec match**: driver §"Message Patterns — Subscriptions" + §"Transports —
  Streamable HTTP" (long-lived POST stream rows).
- **Usefulness**: every dashboard/watcher integration needs exactly this loop;
  the client side shows `McpClient::subscriptions_listen` + `SubscriptionStream`.

### 2. `mrtr-elicitation-server` (+ client leg in the same README)

- **Why**: MRTR (`InputRequiredResult` → retry with `inputResponses`) replaces
  ALL server-initiated requests (elicitation, sampling, roots) on 2026 — the
  second-biggest shift — and only test code shows the round trip.
- **Learning value**: emitting `McpError::InputRequired` from a tool/resource/prompt,
  the capability gate (-32003) and mode-aware sub-capabilities
  (`elicitation.url` vs form-only), echoing `requestState` verbatim, and the
  client legs (`call_tool_with_input_responses`, `read_resource_with_input_responses`,
  `get_prompt_with_input_responses`).
- **Spec match**: driver §"Message Patterns — MRTR" + §"Client Features"
  (elicitation/sampling/roots tables).
- **Usefulness**: any tool needing user confirmation/credentials mid-call —
  the most common "how do I ask the user something?" question.

### 3. `request-scoped-observability-server` (progress + logLevel)

- **Why**: on 2026, progress and log delivery are PER-REQUEST opt-ins
  (`_meta.progressToken`, `_meta` `logLevel`) — a sharp contrast with 2025's
  session-level `logging/setLevel`, and currently shown only in wire tests.
- **Learning value**: `SessionContext::notify_request_progress` (token echo,
  no-token = silence), `notify_log` under the per-request threshold, and how
  notifications ride the POST SSE response frame before the final result.
- **Spec match**: driver §"Message Patterns — Progress" + §"Server Utilities —
  Logging" (logLevel gating rows).
- **Usefulness**: long-running tool UX — the first thing a production tool
  author asks for after "hello world".

### 4. `browser-facing-server` (Origin policy + CORS)

- **Why**: ADR-031 turned Origin validation ON by default; a browser app on a
  different origin now needs a conscious `OriginPolicy::AllowList` decision —
  worth one runnable example so nobody learns it from a 403.
- **Learning value**: DNS-rebinding threat model in two paragraphs;
  `origin_policy(AllowList)` + CORS layering (server-side rejection vs
  browser-side consent); when `Disabled` is correct (API-gateway-fronted).
- **Spec match**: driver §"Transports — Streamable HTTP" (Origin MUST row).
- **Usefulness**: anyone serving MCP to a web UI hits this on day one.

### 5. `oauth-scoped-server` (extend `oauth-resource-server`)

- **Why**: scope enforcement (`with_required_scopes` → 403 insufficient_scope)
  and the 400/401/403 challenge taxonomy just landed and the existing OAuth
  example predates all of it.
- **Learning value**: the full RFC 9728/6750 surface in one place — PRM
  well-known routes, 401 missing vs 400 malformed vs 403 insufficient-scope,
  and why offline_access never appears in advertised scopes.
- **Spec match**: driver §"Authorization" (Token Handling / Insufficient Scope
  / Error Handling rows).
- **Usefulness**: the reference deployment recipe for protected MCP servers.
  (Could be folded into `oauth-resource-server` as an update instead of a new
  example — recommendation depends on the audit's verdict on that example.)

### 6. `bilingual-fleet-client`

- **Why**: the migration story — one client binary talking to a mixed
  2025/2026 fleet — is ADR-030's whole point, demonstrated only in tests.
- **Learning value**: `connect()` negotiation (server/discover → -32601/-32004
  fallback), what locks per-connection, version-conditional features, and
  rolling-upgrade sequencing (servers first, clients never blocked).
- **Spec match**: driver §"Versioning and Compatibility" (backward-compat rows).
- **Usefulness**: every operator running more than one MCP server during the
  2025→2026 transition.

### 7. `header-bound-tools-server` (x-mcp-header / Mcp-Param)

- **Why**: SEP-2243's `x-mcp-header` annotations let infrastructure route on
  tool arguments (region pinning, tenant sharding) — a genuinely new 2026
  capability with zero examples.
- **Learning value**: annotating an input schema property with
  `x-mcp-header`, what the client mirrors into `Mcp-Param-*` (and the base64
  sentinel for non-tchar values), and the -32001 mismatch contract.
- **Spec match**: driver §"Server Features — Tools" (x-mcp-header rows) +
  §"Transports" (SEP-2243 header rows).
- **Usefulness**: API-gateway and multi-region deployments — the headers exist
  precisely so LBs can route without parsing JSON bodies.

### 8. `completion-provider-server`

- **Why**: `completion/complete` now actually routes to registered
  `McpCompletion` providers (it returned hardcoded placeholders until
  2026-06-11); `completion-server` predates provider routing.
- **Learning value**: implementing `McpCompletion` (reference matching,
  `can_handle`, priority), the 100-item cap with `total`/`hasMore`, and
  prompt-argument completion end to end.
- **Spec match**: driver §"Server Utilities — Completion".
- **Usefulness**: IDE-grade argument autocomplete is the feature's entire
  reason to exist. (Likely an update/replacement of `completion-server`
  rather than a new package — see the audit's verdict.)
