# ADR: Compile-Time Schema Generation for MCP Tools

## Status: MANDATORY ✅ COMPLETE

## Core Rules

1. **All schemas**: `type: "object"` at root level (MCP requirement)
2. **Explicit types**: Use `#[tool(output = Type)]` for detailed schemas  
3. **Zero-config output**: Use `additionalProperties: true` for flexibility (output schemas only — input schemas are closed, see § Input schema strictness)
4. **Type mapping**: f64→number, String→string, bool→boolean, structs→object
5. **Field names**: primitives→"output", structs→camelCase, custom→user-specified

## Schema Examples

### String Output (Zero-config)
```rust
// Schema: {"type": "object", "additionalProperties": true}  
// Output: {"output": "Hello, Alice!"}
```

### Struct Output (Explicit type)
```rust
#[tool(output = CalculationResult)]
// Schema: {"type": "object", "properties": {"calculationResult": {"type": "object", "properties": {...}}}}
// Output: {"calculationResult": {"sum": 42.0, "operation": "addition"}}
```

### Struct Output (Zero-config) 
```rust
// Schema: {"type": "object", "additionalProperties": true}
// Output: {"calculationResult": {"sum": 42.0, "operation": "addition"}}
```

## Implementation Status: ✅ COMPLETE with Known Limitations

- Type mapping fixed (f64→number, String→string, bool→boolean)
- Zero-config uses `additionalProperties: true` for flexibility
- Explicit types use detailed property schemas (for self-referential types only)
- Tool descriptions use readable format ("Struct Calculator")
- All MCP Inspector validation errors resolved
- Custom output field names working (`output_field = "tileMetadata"`)

### Current Limitations

#### Detailed Schema Generation for External Types
**Status**: ✅ **RESOLVED via Schemars Integration**

The `#[tool(output = Type)]` syntax now supports three schema generation paths:

1. **Schemars integration** (with `#[derive(JsonSchema)]`): Detailed schemas for any external type
2. **Self introspection** (when `output = Self` or omitted): Detailed schemas via compile-time analysis
3. **Fallback** (external types without JsonSchema): Generic object schemas

```rust
// ✅ Detailed schema with schemars
#[derive(Serialize, Deserialize, JsonSchema)]  // Add JsonSchema derive
pub struct TileMetadata { ... }

#[derive(McpTool, Clone)]
#[tool(name = "get_tile", output = TileMetadata, output_field = "tileMetadata")]
struct GetTileTool { ... }

// Generates: {"tileMetadata": {"type": "object", "properties": {"tile_id": {...}, ...}}}

// ✅ Detailed schema with Self introspection (no schemars needed)
#[derive(McpTool, Clone, Serialize, Deserialize)]
#[tool(name = "calculator")]  // No output specified = defaults to Self
struct Calculator {
    #[param] pub a: f64,
    #[param] pub b: f64,
    pub result: f64,  // Output field
}

// ⚠️ Generic fallback (external type without JsonSchema)
#[derive(Serialize, Deserialize)]  // NO JsonSchema
pub struct TileMetadata { ... }

// Generates: {"output": {"type": "object", "additionalProperties": true}}
```

**Root Cause**: Rust procedural macros cannot introspect external struct definitions during compilation. The `generate_enhanced_output_schema` function can only analyze the struct being derived on.

**Current Workaround**: Use `additionalProperties: true` for flexibility, which works at runtime but provides less precise validation for MCP clients.

#### Proposed Solution: Runtime Schema Generation

**Approach**: Generate detailed schemas on first tool execution based on actual returned data structure.

**Benefits**:
- Works for any struct type (including external crates)
- Accurate schemas based on real data
- No compile-time limitations
- Better MCP client validation

**Implementation Plan**:
1. Analyze JSON structure on first execution
2. Generate detailed schema with proper field types
3. Cache for subsequent calls
4. Fallback to compile-time schema if analysis fails

**Impact**: This would solve the MCP Inspector validation issue for complex struct return types while maintaining backward compatibility.

## Input schema strictness

**Decision.** A tool generated by `#[derive(McpTool)]`, `#[mcp_tool]` or `tool!{}` has a
closed, fully checked input contract:

1. Its `inputSchema` carries `additionalProperties: false`.
2. Its generated `McpTool::call` refuses an argument that is **undeclared**, **missing**
   (required) or **of the wrong type** — optional arguments included. Absent or `null`
   is "not provided" for an optional argument; anything else must convert to the
   declared type.
3. The refusal is a tool result with `isError: true` whose text names each offending
   argument (undeclared keys sorted). It is **not** a JSON-RPC `-32602`.

**Why a result, not `-32602`.** schema.ts, `CallToolResult.isError`: errors that originate
from the tool "SHOULD be reported inside the result object, with `isError` set to true,
_not_ as an MCP protocol-level error response. Otherwise, the LLM would not be able to
see that an error occurred and self-correct", and the schema's own example for
`CallToolResult` is "Invalid tool input error" as an `isError` result. Protocol errors are
for finding the tool or an unsupported method. The published page (server/tools § Error Handling) agrees: protocol errors are for an
unknown tool, malformed requests that fail the `CallToolRequest` schema, and server
errors; "Input validation errors" are Tool Execution Errors reported with `isError: true`.
`arguments` is `{ [key: string]: unknown }`, so an undeclared or wrong-typed argument is a
well-formed request. The same page recommends `{"type":"object","additionalProperties":false}`
for a tool with no parameters and requires servers to "Validate all tool inputs". The spec decides; the earlier
"required-argument failures are JSON-RPC errors" behaviour of generated tools departed
from it and is changed in the same slice, so there is one argument-failure path.

**Why at all.** Argument extraction read only declared keys and discarded a wrong-typed
optional value, so `{"limt": 5}` or `{"limit": "5"}` ran the call with `limit` defaulted
and the caller was never told.

**Owner.** `turul-mcp-derive/src/utils.rs`: `generate_close_input_schema`,
`generate_undeclared_arg_check`, `generate_optional_extraction` (optional parameters go
through the required-parameter conversion; there is no second conversion path) and
`generate_argument_errors_as_tool_result`, used by all three macros. The undeclared
check reads `HasInputSchema::input_schema(self).properties`, not a second list of names,
so behaviour and the advertised schema cannot drift. Only `MissingParameter`,
`InvalidParameterType` and `InvalidParameters` are mapped to the result; every other
`McpError` (MRTR `InputRequired`, `MissingRequiredClientCapability`, ...) still
propagates as a JSON-RPC error.

**Nested objects.** Only the top-level argument object is closed. A nested argument is the
user's own type, converted by serde, so whether it refuses unknown keys is that type's
contract: `#[serde(deny_unknown_fields)]` makes an unknown nested key an `isError`
result naming the argument; a type without it keeps ignoring them. The framework does
not rewrite nested schemas.

**Scope.** Derive-generated tools only. `ToolBuilder` and hand-written `McpTool` impls own
their own `call` and schema and are unchanged; the server does not validate arguments
against `inputSchema` generally. Framework-reserved MRTR keys travel in session
extensions, not in `arguments`, so they are not affected.

**Compatibility.** Behaviour change for clients of derived tools: extra keys and
wrong-typed optional values that used to be ignored now yield an `isError` result, and
missing/wrong-typed required arguments now yield an `isError` result instead of
`-32602`. Shipped as a patch on the 0.4 line; the CHANGELOG entry records the
classification.
